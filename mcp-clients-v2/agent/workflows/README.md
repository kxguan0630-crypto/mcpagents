# Agent Workflow 说明

> 这份说明是给开发者看的。目标不是增加 Agent 的复杂度，而是明确每一层应该负责什么。

## 1. 四层职责

```text
用户输入
   ↓
LLM
   ↓
LangGraph Workflow
   ↓
MCP Tool
   ↓
业务 API
```

### LLM：理解用户

LLM 负责：

- 理解用户想做什么；
- 从自然语言中提取业务参数；
- 判断用户是在回答当前问题，还是提出新的请求；
- 选择合适的业务 Workflow。

LLM 不负责保证确定性的业务前置条件。

### LangGraph：控制流程

Workflow 负责：

- 当前流程处于哪一步；
- 哪些信息已经收集；
- 哪些问题必须询问；
- 哪些工具调用被允许；
- 某个分支是否应该跳过。

例如：

```text
need_design = 1
    ↓
跳过处方流程
```

```text
need_design = 0
    ↓
必须询问是否提供处方
```

### MCP Tool：执行一个明确动作

MCP Tool 应该尽量表达一个清晰的业务动作，例如：

- 查询患者；
- 创建病例；
- 查询订单；
- 获取产品；
- 图片识别；
- 保存/更新面诊资料；
- 创建订单。

Tool Description 可以说明参数、返回值、调用前提和重要的单工具约束，但不应该再承担整个多轮 Agent Workflow。

### 业务 API：真正落库/执行

Server 最终调用现有业务 Service/API。Agent 重构不改变这些业务 API 的职责。

## 2. 病例创建

```text
收集患者信息 + 主诉
        ↓
get_patients_by_name_and_phone
        ↓
用户明确选择
   ┌────┴────┐
 新建患者   使用已有患者
   │           │
   └────┬──────┘
        ↓
     case_add
```

不能因为 LLM 认为“应该是新患者”就跳过患者查询。

## 3. 订单创建

```text
订单检查
  ↓
产品列表
  ↓
need_design
  ↓
诊断：必须询问（可以跳过）
  ↓
影像：必须询问（可以跳过）
  ↓
模型：必须询问（可以跳过）
  ↓
need_design = 0 ?
  ├─ 是 → 询问处方（可以跳过）
  └─ 否 → 完全跳过处方
  ↓
case_order_add
```

“必须询问”和“必须提供”是两个不同概念：诊断、影像、模型以及 `need_design=0` 时的处方，都是必须询问，但用户可以选择不提供。

## 4. 影像

影像不是订单的私有步骤，而是可复用的业务能力。

```text
订单创建流程 ─────┐
                   ├→ image_process → 识别结果 → 保存/更新
订单完成后补影像 ──┘
```

用户直接上传图片时，HTTP Input 层负责把前端文件/引用标准化为 `attachments`；Workflow 决定是否处理；`image_process` 负责识别。

`image_process` 单次最多处理 4 张图片，因此批处理属于确定性的代码规则，而不是让 LLM 自己计算。

## 5. 重要原则

1. **不把业务流程继续塞进单个 MCP Tool Description。**
2. **不把确定性的业务门禁交给 Prompt。**
3. **不把图片二进制塞进 LangGraph checkpoint。**
4. **不为了 Agent 重构修改现有业务 API。**
5. **每个 Workflow 尽量短、直白、有中文注释。**
6. **宁可多写一个容易理解的函数，也不引入一个难懂的通用状态机框架。**
